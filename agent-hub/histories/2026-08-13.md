# 2026-08-13 — Light/Dark mode (issue #65)

**Branch:** `feature/65` (off `main`), tracked via
[#65](https://github.com/datvt243/datvt243.github.io/issues/65).

## Goal

User asked for a Light/Dark mode toggle, "mỗi mode là css riêng" (each mode is
its own CSS), designed so more modes (e.g. a future Dracula mode) can be added
later without restructuring. Scope for this issue: Light + Dark only.

Clarified upfront with the user: default mode is **dark** (matches current
look, no visual change for existing visitors until they opt in), toggle lives
in the **header**, and persistence is via **localStorage** (not a cookie —
accepted tradeoff: no SSR-safe no-flash guarantee, simpler implementation).

## What was done, in order

1. **Discovered the site already had the pieces wired for this, unused**:
   `tailwind.config.js` already sets `darkMode: ['selector']`, and `@nuxt/ui`
   auto-installs `@nuxtjs/color-mode` (`installModule('@nuxtjs/color-mode',
   { classSuffix: '' })` in its own module code) — meaning `useColorMode()` was
   already globally auto-imported and a `.dark`/`.light` class mechanism on
   `<html>` already existed, just never used. Built on top of this instead of
   writing a bespoke composable/localStorage solution.

2. **Split `themes/portfolio-dev/tokens.css` into per-mode files**:
   - `themes/portfolio-dev/tokens/dark.css` — the site's existing slate/orange
     palette, scoped to `:root, .dark` (kept as the fallback/default).
   - `themes/portfolio-dev/tokens/light.css` — new light palette (same slate
     scale inverted + darker orange-600/500 accent shades for contrast on a
     white background), scoped to `.light`.
   - `tokens.css` itself is now a thin aggregator: `@import`s both mode files
     and keeps only the mode-independent token (`--theme-font-mono`). Adding a
     future mode (Dracula, etc.) = one new `tokens/<name>.css` + one `@import`
     line + wiring the toggle to a 3rd option.

3. **`nuxt.config.ts`**: added a top-level `colorMode: { preference: 'dark',
   fallback: 'dark' }` — merges with `@nuxt/ui`'s inline `classSuffix: ''`, sets
   the default so existing users see no change.

4. **`themes/portfolio-dev/layout/Header.vue`**: added a toggle button
   (`useColorMode()`, flips `colorMode.preference` between `'dark'`/`'light'`)
   using two static `<UIcon>`s behind `v-if`/`v-else` (`fe:sunny-o` /
   `fe:moon`) — **not** a single `:name="ternary"` binding, see bug below.
   Placed after the desktop nav / before the mobile hamburger spacer so it's
   visible at all breakpoints.

5. **Fixed a pre-existing hardcoded-color bug found while verifying**:
   `server/plugins/RenderHTML.ts` pushed a literal `class="bg-slate-950
   text-white"` onto `<body>` (predates the theme-token system) — this
   invisibly matched the old dark-only palette but broke light mode (body
   background stayed near-black while the header correctly went white).
   Changed to `class="bg-theme-panel text-theme-text"`.

## Bug found & fixed while verifying (not part of the original ask)

`npm run build`'s prerender step (which actually runs the *trimmed*
`.output/server` to statically generate `/contact`, per its `prerender: true`
route rule) started failing with `Cannot find module
'@iconify-json/fe/icons.json'` / `'@iconify-json/grommet-icons/icons.json'`.

- **Root cause, confirmed by bisection** (via a throwaway `git worktree` on
  `main` to prove it built clean there, then swapping individual changed files
  back to their `HEAD` version one at a time and rebuilding): reverting
  `Header.vue` alone did **not** fix it; reverting only the new `colorMode:`
  block in `nuxt.config.ts` did. That addition apparently shifted Nitro's
  dependency-tracing/tree-shaking enough that icons some pages already
  resolved dynamically (`contact/Index.vue` has a pre-existing
  `:name="`grommet-icons:${...}`"` binding) stopped being statically bundled,
  falling back to a runtime `require()` of the raw iconify collection package
  — which isn't in `.output/server`'s dependency tree because
  `@iconify-json/fe`/`@iconify-json/grommet-icons` were **devDependencies**,
  and Nitro's prerender step runs the already-trimmed production server, not
  the full dev `node_modules`.
- Confirmed this is a **real, shipped defect**, not just a noisy build log:
  the generated `.output/public/contact/index.html` literally contained the
  `Cannot find module` error text baked into the static HTML.
- Confirmed via the same worktree test that this did **not** happen on `main`
  before this work — a genuine regression introduced by the `colorMode`
  config addition (even though the config itself is unrelated to icons).
- **Fix**: moved `@iconify-json/fe` and `@iconify-json/grommet-icons` from
  `devDependencies` to `dependencies` in `package.json` (the standard fix for
  this class of `@nuxt/icon` error). Rebuilt clean 3x in a row afterward,
  confirmed `.output/public/contact/index.html` no longer contains the error
  string.
- Left the underlying dynamic icon-name binding in `contact/Index.vue`
  untouched — out of scope for this issue, and no longer causing a build
  failure now that the collection packages are always available at runtime.

## Possible next steps

- Dracula (or any other) mode: add `themes/portfolio-dev/tokens/dracula.css`
  scoped to `.dracula`, one `@import` line in `tokens.css`, and extend the
  Header toggle from a 2-way flip to a cycle/dropdown across the mode list —
  deliberately not built now, out of scope per the user's "trước tiên chỉ làm
  light/dark" instruction.
- localStorage-only persistence means a light-mode user will see a brief dark
  flash on hard reload/first paint before JS applies the class (accepted
  tradeoff per the user's explicit choice over a cookie-based SSR-safe
  approach) — worth revisiting if it's reported as annoying in practice.
- The pre-existing dynamic `:name="`grommet-icons:${...}`"` binding in
  `contact/Index.vue` (and similar patterns elsewhere, if any) remain
  fragile — they only work now because the collection packages are
  unconditionally bundled; worth an eventual pass to convert to static
  literal bindings (like the `v-if`/`v-else` pattern used in this work's
  Header toggle) so they don't depend on that.
