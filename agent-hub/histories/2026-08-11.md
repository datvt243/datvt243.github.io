# 2026-08-11 — Theme isolation: "editor" UI → swappable `themes/portfolio-dev/`

**Branch:** `design/theme-isolation` (off `main`), all work below is **uncommitted**.

## Goal

User wants to be able to add a completely different UI in the future by touching
one path/config value, instead of hand-editing every page and component. Starting
point: the site's "editor" look (file-tree sidebar, tab bar, JSON/code-block
rendering, jetbrains-mono, slate/orange palette) was baked directly into ~20+
content files as literal Tailwind classes and ad-hoc markup.

## What was done, in order

1. **Design tokens** (`themes/editor/tokens.css`, now `themes/portfolio-dev/tokens.css`)
   — CSS custom properties for the palette (`--theme-panel`, `--theme-border`,
   `--theme-muted`, `--theme-accent`, `--theme-font-mono`, …), RGB triplets so
   Tailwind opacity modifiers (`/50`) still work. Wired into `tailwind.config.js`
   as `colors.theme.*` via `rgb(var(--theme-x) / <alpha-value>)`, and into
   `nuxt.config.ts`'s `css:` array.

2. **Migrated literal classes → semantic classes** across ~21 files (`resumeObject/`,
   `github/`, `post/`, `PostCategories.vue`, `pages/projects|contact|blogs`):
   `font-jetbrains`→`font-theme-mono`, `bg-slate-900`→`bg-theme-panel`,
   `border-slate-800`→`border-theme-border`, `orange-400`→`theme-accent`, etc.
   Deliberately **left alone** (not theme-owned, pre-existing/unrelated):
   `error.vue`'s dead pink/indigo button, `ListRender.vue`'s dead
   `orange-800`/`sky-500` empty-state, `text-blue-400`/`text-red-400` (treated as
   neutral status colors, not theme identity), `components/github/part/Language.vue`
   and `components/post/RelatedArticles.vue` (already-unused dead code, verified
   via grep, moved along for tidiness but not otherwise touched).

3. **Moved structural chrome** `components/editor/*` (8 files: Panel, Folder,
   NavItem, FilterFolder, CodeBlock, TabBar, StatusBar, CornerFrame) →
   `themes/editor/components/`, renamed tags `Editor*` → `Theme*`. Added
   `ACTIVE_THEME` const in `nuxt.config.ts` driving both the `components:` dir
   and the `css:` tokens path.

4. **Renamed `themes/editor/` → `themes/portfolio-dev/`** (user's requested name),
   updated `ACTIVE_THEME` and `CLAUDE.md` accordingly.

5. **Full page-content decoupling** (user explicitly chose the broad scope: "toàn
   bộ markup trình bày" counts as theme, not just the 8 chrome primitives):
   - Moved `components/resumeObject/`, `components/github/`, `components/post/`,
     `components/PostCategories.vue`, `components/base/Heading.vue` (→
     `PageHeading.vue`) into the theme. Renamed all consumer tags
     (`ResumeObjectHero`→`ThemeResumeObjectHero`, `Github`→`ThemeGithub`,
     `PostDetail`→`ThemePostDetail`, etc.) using a `<Tag`/`</Tag`-anchored regex
     (not blind text substitution — `Post`/`Github` etc. also appear as TS type
     names like `import type { Post }`, which must NOT be touched).
   - Extracted the inline `<template>`+logic still living directly in
     `pages/contact.vue`, `pages/projects.vue`, `pages/blogs/index.vue` into new
     theme components (`ThemeContact`, `ThemeProjects`, `ThemeBlogs`), matching
     the pattern `pages/index.vue`/`pages/github.vue` already used (page = SEO
     meta + maybe route-param fetch, template = exactly one `Theme*` tag).
   - `pages/blogs/[id].vue` kept its `useFetch(.../detail/${id})` (route-param
     driven) but the `container-block !pt-0` wrapper moved into `ThemePostDetail`.
   - **`components/ListRender.vue` is the only thing left outside the theme** —
     judged to be a generic loading-state behavior wrapper, not theme content.

6. **Split the theme into `pages/` vs `components/`** (user wanted page-content
   folders visually distinguishable from reusable chrome, for easier navigation):
   - `themes/portfolio-dev/pages/{resumeObject,github,post,contact,projects,blogs}/`
     — one folder per route's content (including `resumeObject/`, added for
     consistency after asking the user — every folder a `pages/*.vue` file
     renders directly lives here).
   - `themes/portfolio-dev/components/` — the 8 chrome primitives +
     `PostCategories.vue` + `PageHeading.vue`.
   - `nuxt.config.ts`'s `components:` array now registers **two** theme dirs
     (`.../pages` and `.../components`), both prefixed `Theme` — Nuxt's
     directory-based naming means tag names didn't need to change at all for
     this step, just physical file moves + one config line.

## Contract for adding a future second theme (to prove the swap actually works)

A new theme = `themes/<name>/` containing:
- `tokens.css` — same CSS variable names as `themes/portfolio-dev/tokens.css`,
  different values.
- `pages/{resumeObject,github,post,contact,projects,blogs}/` — a component for
  every `Theme*` tag each top-level `pages/*.vue` file renders (see
  `CLAUDE.md`'s "UI Theme" section for the exact tag list).
- `components/` — the 8 chrome primitives + `PostCategories`/`PageHeading`, same
  prop/slot contract as `themes/portfolio-dev/components/`.

Then flip `ACTIVE_THEME` in `nuxt.config.ts`. No file under the top-level
`pages/` should need to change.

## Follow-up 2 — fixed `gd` not jumping to Vue components in Neovim

Not a repo-code change — the fix lives in the user's global Neovim config
(`~/.config/nvim`, a separate git repo, clean working tree before/after).

- **Root cause:** `~/.config/nvim/lua/custom/plugins/lsp.lua`'s LSP `servers`
  table had no server attached to the `vue` filetype at all (only `ts_ls`, which
  by default only attaches to `.ts`/`.js`). `gd` is mapped to
  `vim.lsp.buf.definition`; with no client attached to `.vue` buffers it just did
  nothing. (Double-checked `.nuxt/components.d.ts` was NOT the problem — it was
  already correctly generated/up to date after all the theme-folder moves above.)
- **Fix:** added `vue_ls` (official Vue Language Server, hybrid mode) to
  `servers`, and extended `ts_ls` with `filetypes` including `'vue'` plus
  `init_options.plugins` pointing at `@vue/typescript-plugin` (bundled inside the
  Mason-installed `vue-language-server` package, standard path
  `.../mason/packages/vue-language-server/node_modules/@vue/language-server`).
  `vue_ls` isn't in Mason yet — `mason-tool-installer`'s `ensure_installed` picks
  it up automatically from `vim.tbl_keys(servers)` on next Neovim start (verified
  mason-lspconfig's `filetype_mappings.lua` already knows the `vue_ls` name).
- **Next step (user's side):** restart Neovim once so Mason installs
  `vue-language-server`; confirm via `:LspInfo` on a `.vue` file that both
  `ts_ls` and `vue_ls` attach, then re-test `gd` on a component tag.

## Follow-up 5 — stale-while-revalidate for `/blogs`

**Goal:** user reported `/blogs` feels slow every time they navigate to it
(external blog API is slow) — wanted: show last-successful data instantly on
re-entry, silently refetch in the background, overwrite once it arrives.

**What was done** (`themes/portfolio-dev/pages/blogs/Index.vue`):
- Gave the `useFetch` call an explicit stable `key` (`blogs-posts:<category>:
  <page>:<perPage>`) and a custom `getCachedData: (key, nuxtApp) =>
  nuxtApp.payload.data[key]`. Nuxt's *default* `getCachedData` only reads from
  the SSR/static payload during hydration — it does not persist across plain
  client-side re-navigation, which is the actual reason every revisit refetched
  from scratch. Reading `nuxtApp.payload.data` directly (it survives for the
  whole SPA session) fixes that.
- Added an `onMounted` hook that calls `refresh()` when `status` is already
  `'success'` (i.e. we're showing cached data from a prior visit), to
  revalidate in the background and overwrite `data`/the cache once it resolves.
- Added a `listStatus` computed (`blogs.value ? 'success' : status.value`)
  passed to `<ListRender>` instead of raw `status`, so the background refresh
  (which flips `status` to `'pending'`) doesn't flash the list back to the
  loading skeleton while stale data is still being shown.
- **Bug found & fixed while verifying:** Nuxt's page Suspense/transition setup
  calls `onMounted` *twice* for the same single navigation (confirmed via
  instance-id + timestamp tracing — not something introduced by this change,
  and not timing/race related, since it reproduced identically across runs).
  A naive dedupe based on "is a fetch currently in-flight" doesn't catch this
  reliably, because the first background fetch can finish before the second
  `onMounted` call happens. Fixed with a plain `hasRevalidated` boolean scoped
  to the component instance (set synchronously, no timing dependency) — one
  revalidation per real visit, and it's *not* permanently stuck off, since a
  fresh mount (a later, genuine re-visit) gets a fresh `hasRevalidated = false`.

**Current state:**
- `npx eslint --fix` clean, `npm run build` clean.
- Verified via the user's Chrome (CDP :9888), driving actual click-based
  client-side navigation (not full `Page.navigate` reloads, which would bypass
  the client cache entirely and not exercise the real bug): cold load → 0
  browser-visible requests to `/api/blogs/posts` (fetched server-side during
  SSR); 2nd visit → exactly 1 background request, content visible instantly
  (screenshotted mid page-transition, confirming it's cache-instant, not
  waiting on network); 3rd visit → exactly 1 background request again (not
  permanently suppressed after the first revalidation).
