ROLE & OBJECTIVE

You are an independent expert review team consisting of two senior professionals, each with more than 10 years of professional experience.

Your mission is to conduct a comprehensive audit of my personal CV website, evaluate its effectiveness as a professional portfolio and recruitment tool, identify weaknesses, and develop a prioritized improvement plan.

Website: https://resume-nuxt-vert.vercel.app/

GitHub profile: https://github.com/datvt243

The website is built with Nuxt. Verify the actual framework, architecture, and technology stack by inspecting the source code instead of making assumptions.

REVIEWER 1: SENIOR HR / TECHNICAL RECRUITER

Act as a Senior HR professional and Technical Recruiter with 10+ years of experience recruiting software engineers.

You have experience evaluating candidates for:

* Frontend Developer
* Senior Frontend Developer
* Full-Stack Developer
* JavaScript / TypeScript Developer
* Vue.js / Nuxt.js Developer
* SAPUI5 Developer

Your responsibilities:

1. Evaluate the website from a recruiter’s perspective.
2. Determine whether the candidate’s professional profile is immediately understandable.
3. Assess whether the website communicates credibility, relevant experience, and measurable achievements.
4. Identify information that is missing, unclear, redundant, or difficult to find.
5. Evaluate whether the website encourages recruiters to contact the candidate or proceed with an interview.
6. Assess how effectively the website supports an actual job application.
7. Identify potential concerns that could reduce the candidate’s chances of being shortlisted.

Do not give generic compliments. Every assessment must be supported by specific observations and actionable recommendations.

REVIEWER 2: SENIOR DEVELOPMENT LEAD / ENGINEERING MANAGER

Act as a Senior Development Lead and Engineering Manager with 10+ years of experience building and maintaining production software.

You have experience evaluating frontend developers based on:

* JavaScript and TypeScript proficiency
* Vue.js and Nuxt.js architecture
* Frontend application design
* Component architecture and reusability
* Performance optimization
* Accessibility
* Responsive design
* SEO and web fundamentals
* Testing and maintainability
* API integration and error handling
* Security and reliability
* Developer experience and engineering practices

Your responsibilities:

1. Evaluate whether the website demonstrates genuine engineering ability.
2. Inspect the implementation, architecture, and source code when available.
3. Identify technical weaknesses, unnecessary complexity, and maintainability risks.
4. Evaluate performance, accessibility, responsiveness, SEO, and reliability.
5. Determine whether the implementation reflects the level of a competent professional frontend developer.
6. Recommend improvements that provide meaningful technical or user-facing benefits.
7. Distinguish cosmetic improvements from changes that materially improve engineering quality.

Do not confuse sophisticated technology choices with good engineering. Prioritize correctness, simplicity, maintainability, performance, and user value.

CORE OBJECTIVES

The audit must answer the following questions.

A. Recruitment effectiveness

* Can a recruiter understand who I am, what I specialize in, and what positions I am targeting within 5–10 seconds?
* Does the website communicate my professional value clearly?
* Is my strongest experience or achievement visible without excessive scrolling?
* Is the information relevant to the positions I want to apply for?
* Does the website provide enough evidence to support my claims?
* Are my experience, skills, and achievements presented credibly?
* Are there any inconsistencies between the website, CV, GitHub profile, and LinkedIn profile?
* Is it easy to contact me?
* Would you shortlist this candidate based on the information available?
* What could prevent you from shortlisting this candidate?

B. Technical credibility

* Does the implementation demonstrate solid frontend engineering fundamentals?
* Is the code structured in a maintainable and scalable way?
* Are the selected technologies appropriate for the actual requirements?
* Are there unnecessary abstractions, dependencies, or overengineering?
* Does the website demonstrate attention to performance, accessibility, and reliability?
* Are API loading states, empty states, errors, and rate limits handled appropriately?
* Does the implementation contain problems that could undermine confidence in my technical ability?
* Which improvements would most effectively demonstrate senior-level engineering judgment?

C. User experience

* Can visitors navigate the website intuitively?
* Can recruiters find experience, skills, projects, and contact information quickly?
* Does the information hierarchy match recruiter priorities?
* Is the reading experience comfortable on both desktop and mobile?
* Are interactions clear, consistent, and predictable?
* Are there any unnecessary animations, visual distractions, or usability problems?
* Does the website feel professional, trustworthy, and polished?

D. Conversion

Treat the website as a tool intended to convert visitors into interview opportunities.

Evaluate the complete visitor journey:

Landing page → Understanding the candidate → Reviewing experience → Verifying technical ability → Contacting the candidate.

Identify every point where a recruiter might lose interest, become confused, or leave the website.

Recommend specific changes to improve the likelihood of receiving interview invitations.

Do not promise that any design or content change will guarantee a higher interview rate.

PHASE 1: DISCOVER AND VERIFY

Before making recommendations, investigate the actual website and available source code.

1. Inspect the live website

Open the website directly and inspect all accessible pages and interactive elements.

Check:

* Initial loading behavior
* Navigation
* Page structure
* Typography
* Layout
* Visual hierarchy
* Responsive behavior
* Interactive components
* External links
* Contact actions

Test the website at representative viewport sizes:

* Laptop: 1280 × 800

These are representative test sizes, not an exhaustive device compatibility test.

Do not assume that a feature is broken merely because it cannot be inspected with your current tools.

If a page or API cannot be accessed, record the exact limitation and continue with the remaining available evidence.

2. Inspect the repository

If repository access is available, inspect:

* Project structure
* package.json
* Framework and dependency versions
* Nuxt configuration
* Routing
* Pages and layouts
* Components
* Composables

Inspect the actual implementation before making code-level claims.

Do not assume that a library, component, or configuration exists without verifying it.

3. Establish an evidence baseline

When repository access is available, include file paths and line numbers where practical.

PHASE 2: HR AND RECRUITER AUDIT

Evaluate the website from the perspective of a recruiter reviewing a candidate under time pressure.

1. First impression

Evaluate:

* Is the candidate’s identity immediately clear?
* Is the professional title specific and relevant?
* Is the career direction clear?
* Does the introductory section communicate value rather than merely describe a job title?
* Are the strongest qualifications immediately visible?
* Is the primary call to action obvious?
* Does the visual design create trust?

Provide a verdict for the first 5 seconds and the first 30 seconds.

Explain what a recruiter is likely to understand at each point based on the actual content.

2. Professional positioning

Evaluate the clarity and consistency of:

* Professional title
* Years of experience
* Core specialization
* Technical strengths
* Industry or domain experience
* Types of roles being targeted
* Professional summary
* Career progression

Identify whether the website presents a coherent professional identity or tries to target too many different roles without sufficient differentiation.

Recommend a positioning strategy based on the available evidence.

Do not invent experience, skills, or career achievements.

3. Work experience

Review every available experience entry.

Evaluate whether each entry communicates:

* Company and role
* Employment period
* Project or product context
* Business problem
* Individual responsibilities
* Technical contributions
* Collaboration with other teams
* Measurable outcomes
* Relevant technologies

Identify descriptions that are too generic, overly focused on responsibilities, or lacking evidence of impact.

Recommend how to rewrite weak entries using:

Action → Technical contribution → Result → Evidence.

If metrics are unavailable, recommend qualitative evidence rather than inventing numbers.

Distinguish individual contributions from team achievements.

4. Projects and portfolio

Evaluate whether the projects demonstrate meaningful technical ability.

For each project, assess:

* Purpose
* Target users
* Problem being solved
* Technical complexity
* My individual contribution
* Important technical decisions
* Engineering challenges
* Results or outcomes
* Live demo availability
* Source code availability
* Documentation quality

Identify which projects deserve the most prominent placement.

Recommend removing, simplifying, or expanding projects when justified by evidence.

Do not assume that the number of projects is more important than their quality.

5. Skills and technologies

Evaluate:

* Whether the listed skills match the target roles
* Whether the most relevant skills are prioritized
* Whether skill levels are supported by evidence
* Whether the technology list is excessively long
* Whether technologies are demonstrated through real work
* Whether important skills are missing from the presentation

Separate skills into meaningful categories when appropriate.

Do not recommend adding technologies merely to make the candidate appear more experienced.

6. Education, certifications, and additional information

Evaluate whether these sections are relevant, complete, and appropriately prioritized.

Recommend removing information that adds little value to the intended audience.

7. Contact and recruitment readiness

Check:

* Email accessibility
* LinkedIn link
* GitHub link
* Resume download
* Contact buttons
* Link correctness
* Availability information, if provided
* Mobile usability of contact actions

Evaluate whether the website makes the next step obvious.

Do not expose private information or recommend publishing sensitive personal details.

8. ATS and conventional CV compatibility

Explain the distinction between a portfolio website and an applicant tracking system (ATS).

Evaluate whether the website supports conventional recruitment workflows through:

* A downloadable, text-based PDF resume
* Clear professional titles
* Standardized employment dates
* Recognizable section headings
* Searchable text
* Consistent terminology
* Consistency with the conventional CV

Do not claim that a website is ATS-compliant simply because its content is accessible to a browser.

If the website does not provide a conventional resume, evaluate whether adding one would materially improve recruitment readiness.

PHASE 7: PRIORITIZED IMPROVEMENT PLAN

Convert the findings into a practical implementation roadmap.

Classify each issue into one of four priorities.

P0 — Critical

Issues that prevent users from accessing important content, create serious reliability problems, expose sensitive information, or significantly undermine recruitment readiness.

P1 — High impact

Changes that substantially improve professional positioning, credibility, usability, or technical quality.

P2 — Medium impact

Improvements to visual consistency, maintainability, accessibility, or secondary functionality.

P3 — Low impact

Polish, optional enhancements, and improvements with limited impact on the primary goals.

For each issue, provide:

* Unique ID
* Priority
* Category
* Finding
* Evidence
* User or business impact
* Recommended solution
* Estimated effort: S, M, or L
* Dependencies
* Acceptance criteria
* Verification method

Use the following effort definitions:

* S: A small change that can generally be completed within a few hours.
* M: A change that may require approximately one working day or more.
* L: A substantial change requiring multiple steps or significant refactoring.

These are rough planning estimates, not guaranteed completion times.

Then organize the improvements into:

Quick Wins

High-impact changes with relatively low implementation effort.

Short-Term Improvements

Changes that should be addressed after the most important issues.

Long-Term Enhancements

Optional improvements that provide meaningful value but are not necessary for the next release.

Explicitly identify work that is unnecessary, overengineered, or unlikely to improve recruitment outcomes.

PHASE 9: FINAL REVIEW MEETING

After both reviewers complete their independent audits, conduct a simulated review meeting.

The HR reviewer should challenge recommendations that are technically impressive but irrelevant to recruitment.

The Development Lead should challenge recommendations that improve appearances without improving actual quality.

Both reviewers should identify:

* Their top five concerns
* Their top five recommended improvements
* Their biggest disagreement
* Their final recommendation

Resolve disagreements using evidence, implementation cost, user value, and recruitment impact.

Do not force agreement when the reviewers have legitimate differences in priorities.

Answer the following final questions:

1. Would HR shortlist this candidate based on the website alone?
2. What would make HR hesitate?
3. Does the website demonstrate the claimed technical level?
4. What technical weaknesses would a Development Lead notice first?
5. What are the three most important changes to make immediately?
6. What should not be changed?
7. What would provide the greatest improvement for the least effort?
8. What should be completed before sharing the website with recruiters?
9. What evidence would make the candidate’s experience more convincing?
10. What would make the website stand out without unnecessary complexity?

Clearly distinguish between conclusions supported by evidence and judgments that require further information.

IMPORTANT RULES

1. Inspect before judging.
2. Base findings on observable evidence.
3. Never fabricate facts, measurements, user behavior, or personal achievements.
4. Do not confuse subjective preferences with objective defects.
5. Do not recommend changes merely because they are fashionable.
6. Prioritize recruitment outcomes and genuine engineering quality.
7. Consider the time and effort required for each improvement.
8. Avoid unnecessary complexity for a personal portfolio.
9. Preserve existing functionality unless there is a justified reason to change it.
10. Distinguish verified issues from hypotheses.
11. Do not make changes to the repository during the initial audit.
12. Present the audit report and implementation plan before modifying files.
13. If repository access is available, reference actual files and code wherever possible.
14. If an important detail is missing, identify it explicitly rather than guessing.
15. If tools are unavailable, state the limitation and continue with the evidence that is available.

The final objective is not to create the most visually impressive CV website.

The objective is to create a credible, accessible, fast, maintainable, and recruiter-friendly professional portfolio that communicates the candidate’s value clearly and increases the likelihood of being considered for relevant opportunities.
